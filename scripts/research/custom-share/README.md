# Custom Share receiver research

This directory is isolated research, not a production receiver and not evidence that Final Cut sent a callback. Never install a custom destination, launch Final Cut, send it Apple Events, or alter its libraries or existing reservation as part of these tests.

From this worktree after dependency installation:

```sh
node --test scripts/research/custom-share/*.test.mjs
xcrun swiftc scripts/research/custom-share/SwiftReceiver.swift scripts/research/custom-share/swift-tests/main.swift -o /tmp/framekit-share-swift-tests
/tmp/framekit-share-swift-tests
```

The mock asset model generates separate identifiers and directories for same-name assets and matches synthetic URLs only; it never creates folders or reads outputs. It does not protect against symlink races or authenticate paths or senders. The standalone Swift harness constructs descriptors locally and directly invokes the handler. Separately, `ipc.test.mjs` compiles a unique temporary executable, starts a test-owned receiver process, verifies the target executable path, and sends synthetic Open Document events only between that receiver and test-owned sender processes using never-interact mode. It verifies that the receiver handler observed each token and returned error -1708, then terminates only its own receiver. It never sends an event to Final Cut or an existing app. Its actual Open Document handler unconditionally rejects the event because sender identity, asset correlation, target and output freshness have not been established. The in-memory lock-protected mock separately exercises concurrent duplicates, stale generations, cancellation and loss of state in a fresh instance (not a process-restart test); it has no persistence, target authentication, output verification or cross-process guarantees. It does not model a documented Final Cut callback token or prove behavior of the actual sender.

This is not yet a functional custom Share destination. Apple documents an app bundle with `com.apple.proapps.MediaAssetProtocol` and scripting definitions plus an asset object, `make`, property getters and Open Document handling. A syntax-only bundle and scripting-definition skeleton can be built locally, but it includes a mock KVC asset class and a lexical URL registry, but maps a Cocoa make command that unconditionally rejects, and does not implement a successful make-event response or resolved native object specifier, verified metadata/data options, scripting access groups, real event-to-asset correlation, or a destination installation. It must not be installed or launched as a Share destination. Apple's prose and example use different asset-management access-group strings; determine the correct entitlement/access-group behavior for the selected SDK and environment before a separately reviewed test rather than treating either spelling as validated. See the official [packaging instructions](https://developer.apple.com/documentation/professional-video-applications/receiving-media-and-data-through-a-custom-share-destination) and [scripting definition](https://developer.apple.com/documentation/professional-video-applications/creating-scripting-definitions-for-custom-share-destinations).

The Node experiments model strict callback ordering, output hashes and journals. Their generated IDs and event semantics are mock assumptions. Both implementations remain unable to authenticate the native sender or bind the callback to an exact Final Cut target/revision, and the earlier Node race and durability limits remain. No result here clears a reservation or demonstrates native operation completion.

Apple's [response protocol](https://developer.apple.com/documentation/professional-video-applications/responding-to-apple-events-from-final-cut-pro) describes an app-supplied `com.apple.proapps.share.id` share-metadata value that Final Cut includes in exported media files for tracking. This is a possible future correlation input, not a documented callback token, authenticated sender, unique project identity or revision digest. The documentation does not establish its availability in an FCPXML-only export, persistence through every format, resistance to copied metadata, or a safe retry/fencing protocol. The same documentation says Final Cut updates the shared project with returned share metadata. Consequently, do not test or enable this metadata path against an existing library under the present no-mutation constraint; even a future isolated native test needs an explicitly authorized, disposable target and operation. This is a documentation observation only: the fail-closed receiver does not return metadata, and no Final Cut operation was performed.

To compile a temporary app without registering or launching it:

```sh
node --test scripts/research/custom-share/package.test.mjs
research_dir=$(mktemp -d -t framekit-share-bundle)
node scripts/research/custom-share/build-bundle.mjs "$research_dir/ShareResearch.app"
```

The build is create-only and limited to the system temporary directory. `plutil` validates the property-list structure; `xmllint` validates the scripting-definition DTD; `sdp` generates a header; and `file` checks the compiled executable. These checks do not validate the behavior, entitlement/access-group spelling, sender authenticity, compatibility, code signing, notarization, or registration with Final Cut. `sdp` itself may return success for erroneous input, so the independently checked DTD is not a substitute for semantic or runtime tests. No app or destination is launched or installed by these commands.

The mock registry can construct an `NSUniqueIDSpecifier` using an explicitly constructed test-only Cocoa class description. The harness checks the descriptor's asset class, unique-ID form and ID value, and rejects a class description whose relationship is absent. It also registers that description for a test-only in-process container and evaluates the specifier against that explicitly supplied container: two same-name assets resolve by their unique IDs, while unknown and duplicate IDs do not resolve. This does not register or resolve an actual app scripting container, successfully handle a real `make` request, decode a descriptor received from another process, or authenticate the caller.

A separate local characterization loads a complete test `.scriptSuite` declaration in memory, verifies that the asset code maps back to the container key, and supplies the test container as the scripting execution context's top-level object. On the tested system, direct object evaluation succeeds but reconstruction from its descriptor returns `nil`. Earlier ad hoc attempts without that top-level context terminated with an Objective-C exception; setting it avoided that exception in this test. Neither observation proves how a correctly configured running app handles a real `make` request or descriptor. Reproduce without starting an app or sending an Apple Event:

```sh
xcrun swiftc scripts/research/custom-share/swift-specifier-tests/main.swift -o /tmp/framekit-share-specifier-tests
/tmp/framekit-share-specifier-tests
```

The separate `sdef-runtime.test.mjs` builds a disposable app bundle with a DTD-validated test SDEF and **no** Final Cut Share capability key, then directly starts its executable. Only another copy of the same temporary executable can be targeted by its sender. In a completed local run, the test suite was absent from the Cocoa scripting registry before a synthetic `make` event, which returned `-1708` without entering the mock command. The test reports a transport timeout as inconclusive. This does not identify why the suite was absent or establish behavior for an installed or properly configured app. The test app is not registered as a Share destination and never contacts Final Cut.

The IPC tests use synthetic strings and separately a list containing a URL descriptor for a test-owned temporary file; they do not observe Final Cut-generated descriptors or authenticate a sender. An alternate rejection-code control is included to investigate repeated handler observations. In local runs using error -1708, one token sometimes reached the handler twice with the same return ID; in a small comparison using error -1701 no repeated token was observed. The cause and generality remain unconfirmed. The test checks at least one observed handler call per sent token and does not claim exactly-once delivery, native duplicate behavior, a completion receipt, or a safe production dispatch boundary.

`ipc-make.test.mjs` separately compiles a unique temporary executable and sends a synthetic `corecrel` event from a test-owned process to another copy of that executable, after checking its executable path. In some runs a test-only raw handler returns an `aset` unique-ID specifier; in others the sender times out without an observed handler entry, even after an Open Document ping succeeds. One exploratory run returned distinct IDs to three concurrent senders, but repeated runs are not reliable. The characterization reports timeouts as inconclusive rather than claiming delivery; a passing test alone does not prove the positive path ran. The reason for intermittent timeouts is unknown. This is a transport/descriptor experiment, not the fail-closed `ResearchMakeCommand`, an actual created or resolvable Cocoa asset, sender authentication, duplicate-event deduplication, a Final Cut callback, or evidence of a working Share destination. The synthetic receiver does not read or write media.

The ping now also queries `AEGetEventHandler` for `corecrel` in the receiver and requires a zero status, showing that an event handler was registered at ping time. This does not identify the registered handler or guarantee later delivery. Four local runs after adding the probe returned specifiers; none reproduced the earlier timeout, so those runs do not explain it or establish reliability.

The test-only raw handler records generated synthetic IDs and supplied names in memory. On a positive run, the sender embeds the returned asset descriptor in a synthetic `locn` property specifier, sends `coregetd`, and checks a typed `aslc` record containing a synthetic file URL, matching base name, description flag and media flag; an unissued ID is rejected. The handler checks descriptor fields directly and installs its get handler after receiving make. This tests only the descriptor shape against the fixture's interpretation of Apple's scripting definition: it does not establish that Final Cut accepts the record or that its URL exists or is safe. There is no Cocoa object-specifier reconstruction, successful Cocoa scripting command, persistence, authentication or actual file output. Make still sometimes times out before its handler runs, which the test records as inconclusive; failures after make are not treated as inconclusive.

In the IPC harness, the receiver reads the documented read-only sender PID and audit-token attributes. It compares each to the test-owned sender PID, resolves a code object using `SecCodeCopyGuestWithAttributes` with the audit token, and checks the resolved path against the exact temporary test executable. It logs only the token length, PID and result codes, not the token bytes. On the tested system, signature validation without an additional requirement succeeds for this test executable, while the deliberately broader `anchor apple` requirement rejects it. This negative control illustrates why signature validity alone is not a sender authorization policy. The follow-up pins the designated requirement observed from the installed 10.7.1 app and tests that it rejects a test sender. It does not observe an Apple Event from Final Cut, validate a live Final Cut process, establish a policy for other versions, bind a sender to an intended project/export, protect against later file replacement, or authorize accepting an event; the receiver still rejects it. See Apple's [guest-attribute documentation](https://developer.apple.com/documentation/security/guest-attribute-dictionary-keys) and SDK Security headers for API scope.

The separate Swift output-inspection experiment uses `open`/`openat` with `O_NOFOLLOW`, file/directory identity checks, a size limit and SHA-256 comparison to an independently supplied expected digest:

```sh
xcrun swiftc scripts/research/custom-share/SwiftOutputVerifier.swift scripts/research/custom-share/swift-output-tests/main.swift -o /tmp/framekit-share-output-tests
/tmp/framekit-share-output-tests
```

Test-owned temporary files exercise wrong digest, missing file, traversal, final-component symlinks and deterministic directory/file replacement. A negative control shows a hard link to an outside test file with the same bytes is accepted. This is not connected to the Apple Event handler; it neither proves that Final Cut generated the file nor authenticates the expected digest, target, content semantics or freshness. It does not establish safety under all concurrent changes, parent-directory aliasing, post-check replacement or power failure; `O_NOFOLLOW` only applies to the checked final components. No production receipt or native operation is inferred.

The static signature check is opt-in and read-only:

```sh
node scripts/research/custom-share/verify-static-signature.mjs '/Applications/Final Cut Pro.app'
```

The pinned requirement is the designated requirement observed from the locally installed 10.7.1 build 410082. The static verification checks the app bytes against this pinned expression; the IPC test separately checks that test-owned senders do not satisfy it. A static match does not prove that a running sender is that app, that other versions have the same signing policy, or that an authenticated sender exported the intended target. The test receiver still rejects incoming events. No code is signed, installed, launched or changed by the verification command.
