## Framekit が管理するプロジェクト

ヘッドレス編集では Final Cut Pro を起動する必要はありません。プロジェクトとタイムラインの状態は Framekit が管理します。エディタへの接続やファイルの書き出しで、その状態が自動的に置き換わることはありません。

## 編集の流れ

1. 実行したい操作を `editing.route` に指定し、実行経路を確認します。
2. ヘッドレス用のツールでプロジェクトを作成するか開き、現在のリビジョンを確認します。
3. 確認したリビジョンを指定してメディアを登録します。`headless.media.search` にプロジェクト ID を渡すと、登録済みの素材を ID、名前、パスで検索できます。同名の素材も個別の結果として返ります。編集内容をプレビューしてから実行します。
4. レンダリングの前に、対象のリビジョンを開き直して内容を確認します。出力も独立して検証してください。

## 編集を取り消す

`headless.edit.execute` が返す `undoId` は保存済みの取り消し記録と結び付いています。そのまま保管してください。取り消すには、プロジェクト、シーケンス、Undo ID、現在の正確なリビジョンを指定して `headless.edit.undo` を呼び出します。新しいリビジョンが保存され、プロジェクトを再読み込みしてタイムラインのダイジェストを検証します。

後続の編集がある場合、記録が失われたか書き換えられた場合、ローカルのメディアが変わった場合は、取り消しが拒否されます。この仕組みは元の ID を保持し、プロジェクトの保存先を信頼できることが前提です。悪意のある呼び出しや保存状態全体の巻き戻しには対応していません。Final Cut Pro 側の操作も対象外です。

## 既存のタイムラインを変更する

現在のリビジョンと、タイムライン上の各クリップの配置を識別する ID（オカレンス ID）を取得します。そのリビジョンと `trim-occurrence`、`split-occurrence`、`remove-occurrence`、`move-occurrence` などの操作を `headless.edit.preview` に渡します。プレビューではプロジェクトに書き込みません。変更後のタイムラインを確認したら、同じ操作を `headless.edit.execute` で実行してください。

時刻は有理数で表します。移動先は表示順ではなくタイムライン上の開始時刻で指定します。リビジョンが古いというエラーが出たら、状態を取得し直してください。名前や表示位置だけでクリップを特定しないでください。プロジェクトの状態とオカレンス ID は MCP サーバーの再起動後も保持されます。

フェード、アタッチメント、ストーリー要素への参照があるオカレンスは、分割後にこれらの対応関係を安全に引き継げないため分割できません。プレビューと実行のどちらでも分割は拒否され、プロジェクトは変更されません。

## 書き出しとレンダリング

`headless.fcpxml.export` は、指定したプロジェクトとシーケンスのリビジョンから新しい FCPXML を生成します。出力先を明示してください。既存ファイルへの上書きは拒否されます。書き出しとレンダリングには、Framekit の状態ディレクトリ内や登録済みの素材と同じファイルを指す出力先は使えません。ラフカットのレンダリング先と FCPXML の出力先にも別々のファイルを指定します。生成した FCPXML は手動で受け渡せます。Final Cut Pro での読み込みと検証は別途行ってください。

リビジョンが古い場合は状態を再確認します。必要なプロバイダーが使えない場合は、その理由がエラーとして返ります。ネイティブ操作や外部レンダラーへの自動切り替えはありません。[動画制作の手順書](https://github.com/morshoto/framekit/blob/main/plugins/framekit/references/tests/codex-video-production-e2e.md)で、各段階の確認方法を参照できます。

ラフカットの実行結果を確認できなかった場合は、再試行する前に [HEADLESS_ROUGH_CUT_HISTORY_UNCONFIRMED](/ja/docs/error-reference/#headless-rough-cut-history-unconfirmed) を確認してください。

## 書き込みロックを扱う

ロックに記録されたプロセスが終了していても、書き込み時に既存のロックを自動削除することはありません。この保護を有効にするには、同じ保存先に書き込むすべてのプロセスがこの動作に対応している必要があります。新しいバージョンと保存先を共有する前に、旧バージョンの書き込みを終了させ、処理が残っていないことを確認してください。旧バージョンが作成中または置き換え後のロックを削除すると、同時書き込みが起こり得ます。

書き込みの中断後にロックが残り、後続の書き込みが止まることがあります。手動で解除する前に、そのロックを使えるプロセスが残っていないことを別の手段で確認してください。経過時間、空のロックファイル、PID だけでは判断できません。

[プロジェクトとタイムライン IR](/ja/docs/projects-and-timeline/) と[リビジョンと安全性](/ja/docs/revisions-and-safety/)も参照してください。
